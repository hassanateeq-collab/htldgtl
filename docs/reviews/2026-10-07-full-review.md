# Full code review — 7 October 2026

Scope: every file in `apps/pms/src`, `packages/shared/src`, the nine migrations, the three SQL suites, the docs, plus the Supabase security/performance advisors and a production build. Method: a line-by-line read of the whole codebase, then three independent audits (database/RLS, frontend architecture, front-desk UX) whose findings were verified against the code and merged here. Nothing was changed as part of the review.

**Verdict.** The foundations that are hard to retrofit are sound: one database with RLS keyed on `tenant_id`, a live-membership check on every read, the no-double-book `EXCLUDE` constraint, write actions as SQL functions, stored folio totals, documented ADRs, and 41 regression checks. What sits on top of them is prototype-grade: the app loads every booking of the hotel on every screen and filters in the browser, money rows can be edited or deleted by any front-desk login, the server uses the UTC date as "today", the state machine lives only inside two functions, and whole front-desk flows (walk-in check-in, check-out with payment, ID capture, taxes, housekeeping, cash, reports, settings) are missing. The visual layer is the default shadcn palette with 10 px labels and 32 px buttons. A rewrite of the application layer and a hardening pass on the schema are the right call; the database design itself stays.

## 1. Findings

Severity: **Critical** = money or data can be lost or corrupted today · **High** = wrong results or a blocking product gap · **Medium** = quality, safety or UX defects to fix in the rewrite · **Low** = hygiene.

### Critical

| # | Finding | Where | Why it matters |
|---|---|---|---|
| C1 | **Payments and charges are editable and deletable by any front-desk login, and folio totals are client-writable.** The write policies on `folios` and `folio_items` are `for all` (insert/update/delete) for owner, manager, front_desk and accounts; `total_charges`, `total_payments`, `balance` are ordinary columns, so `update folios set balance = 0` is a legal API call and `set_booking_status` then checks the guest out on that number. The closed-folio guard only fires on INSERT, so items in a closed folio can be edited or deleted and the totals are silently recomputed. There is no void/reversal concept: a cash receipt can be hard-deleted, leaving only an audit row. | `operational_core.sql:157-159, 261, 408-421`; `booking_actions.sql:137-142` | Cash control is the product's pitch; "receptionist deletes the receipt" is a built-in fraud path. |
| C2 | **Deletes cascade through money.** Front desk can `DELETE` a booking, which cascades to its folio and every payment. Owner/manager can delete a property, which cascades through every booking, folio and payment of the hotel. | `operational_core.sql:103, 155, 167, 389-393`; `platform_core.sql:530-534` | One wrong tap or one hostile owner-level login erases financial history. |
| C3 | **Every list is silently capped at 1,000 rows, and the newest bookings are the ones dropped.** `useBookings` loads all bookings ordered by `check_in` ascending with no range; PostgREST truncates at 1,000 without an error. A 30-room hotel reaches that in a few months, after which the calendar shows booked rooms as free, Today misses arrivals, and detail/edit/receipt screens (which `.find()` the booking in that list) show "Booking not found" — including right after creating a booking. Guest search is client-side over a capped list. | `data/queries.ts:202-215, 280-302`; `screens/BookingDetailScreen.tsx:71`; `EditBookingScreen.tsx:27`; `ReceiptScreen.tsx:23` | Correctness failure that arrives quietly with normal use. |
| C4 | **"Today" is wrong between midnight and 05:00 PKT.** SQL uses `current_date` (UTC on Supabase) to truncate early departures and to default `shift_date`/`due_date`; the client uses the device's local day; `properties.timezone` is fetched and never read. A 01:00 check-out on the 8th sets `check_out` to the 7th and produces a zero-night row; an owner checking from abroad sees a different Today than the desk. | `early_checkout_release.sql:66-71`; `operational_core.sql:187, 213`; `lib/dates.ts:14-16`; `data/queries.ts:256-258` | Night-audit and late-arrival time is exactly when this bites. |

| H6 | **Attribution is client-controlled or missing.** The app's payment insert never sets `posted_by`, so no payment has a cashier; `posted_at` and `created_by` are writable by the client. | `operational_core.sql:115, 175-176`; `data/mutations.ts:71-78` | BEFORE INSERT triggers stamp `posted_by = auth.uid()`, `posted_at = now()`, `business_date`. |

### Medium

**Database**
- M1 In-tenant privilege escalation: `memberships_write` lets a manager make themself owner or remove the last owner (`platform_core.sql:521-525`).
- M2 PII reach: housekeeping and read-only roles read every guest's CNIC/passport; `audit_row()` copies full rows so IDs are duplicated into `audit_log` (`operational_core.sql:377-379`; `platform_core.sql:289-310`).
- M3 `my_tenant_access()` and `tenant_has_feature()` return a tenant's subscription and feature set to anyone whose JWT still carries that `active_tenant`, with no membership check (`platform_core.sql:346-376`).
- M4 Public signup form is unvalidated: no email/phone format, negative `rooms`, anon may write the admin `notes` field (`platform_core.sql:105-119, 505-506`).
- M5 Guest duplication and formats: `create_booking` inserts a new guest whenever `p_guest_id` is null; `guests.phone` is free text despite the `+92` rule; no CNIC format check (`booking_actions.sql:70-77`; `operational_core.sql:86`).
- M6 Overpaid check-out: only `balance > 0` blocks; a deposit larger than the stay closes the folio with money owed to the guest and no refund row (`booking_actions.sql:139`). The UI hides it: `Math.max(balance, 0)` prints "PAID PKR 0" (`BookingDetailScreen.tsx:225`; `ReceiptScreen.tsx:137`).
- M7 Out-of-order rooms are bookable: `create_booking` checks only `is_active` (`booking_actions.sql:64-67`); no date-ranged room blocks.
- M8 RLS cost: every policy calls four helper functions per row; 31 tables evaluate both the read and the `for all` write policy on every SELECT; two policies re-evaluate `auth.uid()` per row (advisor). Wrap helpers in `(select …)`, split policies by command.
- M9 Indexes: unindexed FKs on `bookings.guest_id`, `rooms.room_type_id`, `booking_rooms.room_type_id`, `housekeeping_tasks.room_id` (advisor); no GiST on bookings' date range for calendar overlap queries; no trigram index for guest search.
- M10 `set_active_tenant` writes `auth.users` directly (`set_active_tenant.sql:29-33`) while `data-model.md:56` still says an edge function sets the claim — document the coupling or move to an access-token hook.
- M11 Platform actions unaudited: no audit trigger on `tenants`, `platform_admins`, `platform_plans`, `platform_features`, `platform_plan_features`, `invoice_items`.
- M12 `next_booking_no` regex-scans every booking and restarts at 1001 after a prefix change; `tenant_settings.booking_prefix` is unvalidated (`%` or `_` corrupt the `like`).
- M13 `search_path = public` everywhere; the safe form is `public, pg_temp`.
- M14 The suites depend on a demo seed that is not in git (dates relative to 2026-10-06, literal labels), so they age out and cannot run on a fresh database or in CI; there are no tests for the direct-write bypasses in C1–C2, concurrency, cross-tenant leaf references, the `accounts`/`housekeeping`/`read_only` roles, or the folio state after early departure/cancellation.

**Application**
- M15 Error mapping by message regex; raw Postgres text is shown to receptionists; a network failure on login reads "Email or password is incorrect" (`data/mutations.ts:22-35`; `LoginScreen.tsx:47`; `components/State.tsx:16`).
- M16 i18n leaks: the English kind label is written into `folio_items.description` and later compared against it; hard-coded strings in `data/tenant.tsx:41`, `auth/session.tsx:64`, placeholders, `m²`; manual plurals; `as MessageKey` casts hide missing keys.
- M17 Touch targets and type: `size="sm"` buttons are 32 px and are the primary mobile controls for Add payment/Save/Edit details/calendar nav; eight uses of 10–11 px text; calendar bars ~32 px tall.
- M18 Contrast and colour-only cues: white on `bg-red-400`/`bg-blue-500` fails AA at 12 px; housekeeping state is an 8 px dot with a hover `title` only; red is used for both no-show and money due.
- M19 Layout magic numbers: `h-[calc(100svh-7rem)]` assumes top bar + tabs (the read-only banner breaks it); `pb-24` in nine screens; `env(safe-area-inset-bottom)` is 0 because `index.html` lacks `viewport-fit=cover`.
- M20 Guest search: a query per keystroke, unescaped `ilike` input, name-only, errors ignored; typing a known name without tapping the hit creates a duplicate guest every time.
- M21 Controlled numeric inputs cannot be cleared (`Math.max(1, Number(v) || 1)`); a rate typo becomes a PKR 0 room charge; check-out is not nudged when check-in passes it.
- M22 Filter semantics: no-shows sit in "Current" until their planned check-out; "Free tonight" counts inactive and out-of-order rooms; zero-night early departures vanish from the calendar; `Past` contains cancelled future bookings.
- M23 Shared reception devices: persistent session with no idle lock — a product decision to make explicit.
- M24 Dead dark theme; status colours are raw palette classes, so neither dark mode nor `tenant_branding.primary_color` can be applied.
- M25 Multi-device freshness: `staleTime` 30 s, no realtime or polling — a check-in on one device is invisible on the other until refocus.
- M26 Accessibility: unlabeled hotel-code input; error text without `role="alert"`; no focus management on route change; no `h1` on desktop; calendar cells click-only.
- M27 UX details: hardcoded Back links; `prettySlug` fabricates the hotel name on the login page; receipt "Issued" is the print date, no receipt number, no tax lines, no signature block, logo loaded but not rendered; Guests are tenant-wide while their stats are property-wide; no "New booking for this guest"; sign out with no confirm; dead i18n keys (`booking.roomCharges`, `rooms.star`, …).

### Low
`rate_plans_one_default_idx` enforces at most one default, not exactly one, and `provision_tenant` creates no rate plan or room type; `provision_tenant` gives trials a 30-day period beside a 14-day `trial_ends_at`; `children` and `max_occupancy` are never used; audit noise (one extra audit row per folio recompute, every per-date rate row); trigger ordering relies on alphabetical names; `Button` lacks `type="button"` by default; `ConfirmButton` has no visible countdown; `formatHotelDate` parses dates in UTC; `useMediaQuery` sets state in an effect; `tsconfig.base.json` lacks `noUncheckedIndexedAccess`; no `test` script; two moderate `npm audit` findings in `react-router-dom`; leaked-password protection still off (dashboard toggle); `data-model.md` drift on three points; `supabase/tests/README.md` lists two suites while three exist.

### What is right and stays
RLS pattern with live-membership reads; `EXCLUDE` no-double-book constraint; SECURITY INVOKER action functions; fill triggers for child rows; stored folio totals via trigger; the slug login link and `set_active_tenant` flow; feature-flag entitlements; the ADRs; the migration-mirror discipline; the regression-suite approach (impersonated JWT claims with rollback); React Query + Supabase client architecture; mobile-first with a desktop tier.

## 2. Rewrite plan

Four releases, each committed, verified in the browser at 375 px and desktop, with all SQL suites passing, and each ending at a checkpoint. The schema is hardened and extended, not replaced; the application layer is rewritten.

### Release A — Integrity, business date, data model (migration 10 + tests)
1. **Hotel business date.** `property_today(property_id)` from `properties.timezone`; `check_in_time`/`check_out_time` on properties; every `current_date` replaced. Business date passed to and stamped on folio items and cash shifts.
2. **Append-only folio.** `folio_items` becomes insert-only for tenant roles, with `voided_at/voided_by/void_reason/reverses_item_id`, `category` (`room`, `tax`, `food`, `laundry`, `extra`, `other`, `deposit`, `settlement`, `adjustment`), `service_date`, `business_date`, `receipt_no` (payments/refunds), `cash_shift_id`, server-stamped `posted_by/posted_at`. `void_folio_item()` RPC (owner/manager/accounts, reason required). `recompute_folio` locks the folio row and ignores voided items. Folio totals, status and `closed_at` protected with column privileges; closing happens in the lifecycle trigger. Closed-folio guard on insert, update and delete.
3. **Per-night room charges.** `create_booking` posts one `room` item per night (`service_date`); `update_booking` voids and re-posts; early departure voids unstayed nights; late departure posts the extra nights; cancellation/no-show posts the configured fee (default none) and closes the folio when settled.
4. **Tax.** Per-property `tax_name`, `tax_rate_pct`, `tax_mode` (`none` | `exclusive` | `inclusive`), `tax_applies_to` (room only / all charges); items carry `tax_pkr` computed at posting; folios carry `total_tax`; receipts show subtotal, tax, total. NTN/STRN move to the property.
5. **No deletes of money or stays.** `for all` policies split into insert/update with no delete for tenant roles on bookings, booking_rooms, folios, folio_items, cash_shifts, properties, room_types, rate_plans, guests; `on delete restrict` on the booking → folio → items chain and on properties.
6. **Tenant-safe references.** Composite foreign keys `(tenant_id, …)`/`(property_id, …)` on every leaf reference (H2).
7. **Booking lifecycle in the database.** `for update` in all RPCs; BEFORE UPDATE trigger enforcing transitions and stamping `checked_in_at`, `checked_out_at`, `cancelled_at`, `cancellation_reason`, `no_show_at`; AFTER UPDATE trigger for side effects; check-in requires today within the stay (or moves check-in to today, re-validated by `EXCLUDE`); check-out requires balance ≤ 0 unless an owner/manager override with reason is recorded (the folio then stays open as a receivable); `booking_rooms` kept in step by trigger; `unique (booking_id)` on `booking_rooms` for v1.
8. **Counters.** `property_counters` for booking, receipt and folio numbers (atomic `insert … on conflict … returning`), validated prefix.
9. **Guest identity.** `guests.id_type` (`cnic` | `nicop` | `poc` | `passport` | `other`), `id_number`, `id_expiry`, `address`, plus format checks for `phone` and CNIC; `require_id_at_check_in` property setting enforced in the lifecycle trigger; identity fields stripped from the audit JSON; out-of-order rooms refused by `create_booking`.
10. **Access and platform hardening.** Membership guards (no self-promotion, last owner protected); `tenant_access_level()` honours `tenants.is_active`; `my_tenant_access`/`tenant_has_feature` require membership; property cap enforced; signup form CHECKs; `search_path = public, pg_temp`; helpers wrapped in `(select …)` and read/write policies split; audit triggers on the platform tables; missing indexes (FKs, GiST on booking date ranges, trigram on guests).
11. **Operations primitives.** `open_cash_shift`, `close_cash_shift(declared)`, `confirm_cash_shift(counted)` with expected-by-method computed from linked payments and one open shift per property; `daily_report(property_id, date)`; housekeeping status history and auto "dirty" task at check-out; `run_billing_transitions()` scheduled daily with `pg_cron` (ADR 0004).
12. **Tests.** Suites rebuilt to create their own fixtures inside the transaction (no dependence on seed dates), extended with the direct-write bypasses, concurrency (`for update` behaviour), cross-tenant leaf references, all six roles, folio state after early departure/cancellation/void, tax arithmetic, counters and cash shifts. Types regenerated into `packages/shared`.

### Release B — Application foundation

### Verification and housekeeping

### Open product decisions (defaults chosen; change in Settings)
- Tax: per property, default `none` for new tenants; demo property set to Sindh sales tax on services, exclusive, so the receipt flow can be exercised.
- Early departure: release and void unstayed nights (an "Early departure fee" preset exists for hotels that charge).
- Check-out owing: blocked for front desk; owner/manager override with reason creates a receivable.
- ID at check-in: required by default.
- Shared reception devices: persistent session kept for now; an idle lock is on the list after Release D.
